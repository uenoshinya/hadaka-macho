# CLOSET CHECK 設計書（STEP 1）

> 「なんとなく買う」をなくし、納得して洋服を購入する。

店頭で 2〜5 分でチェックを終えられる、スマートフォン向けの洋服購入サポートアプリです。
Google スプレッドシートをデータベース、Google Apps Script（GAS）をバックエンドにした Web アプリとして作ります。

---

## 1. システム構成

```
 ┌───────────── スマートフォン（ブラウザ） ─────────────┐
 │  Index.html  ← Style.html（CSS）                     │
 │              ← JavaScript.html（画面制御・状態管理）  │
 │                                                       │
 │   google.script.run.xxx()  （非同期通信）             │
 └───────────────────────┬──────────────────────────────┘
                         │ withSuccessHandler / withFailureHandler
 ┌───────────────────────▼──────────────────────────────┐
 │  Code.gs（GAS Web アプリ）                            │
 │   ・CONFIG（設定の一元管理）                          │
 │   ・初期化 / 画面配信 / 判定 / 保存 / 履歴取得         │
 │   ・LockService で保存時の競合を防止                  │
 └───────────────────────┬──────────────────────────────┘
                         │ SpreadsheetApp
 ┌───────────────────────▼──────────────────────────────┐
 │  Google スプレッドシート                              │
 │   Checklist ／ PurchaseHistory ／ Settings            │
 └──────────────────────────────────────────────────────┘
```

### 1-1. 配置形態

- **コンテナバインド型**（スプレッドシートの「拡張機能 → Apps Script」から作るスクリプト）を推奨します。
  - 初心者でも「どのシートに繋がっているか」が分かりやすいためです。
- `CONFIG.SPREADSHEET_ID` が空なら紐付いているスプレッドシートを使い、ID を書けば別のスプレッドシートも使えるようにします。

### 1-2. ファイル構成

リポジトリ内の配置（GAS エディタにはこの 4 ファイルをそのまま貼り付けます）。

```
closet-check/
├── src/
│   ├── Code.gs          … サーバー処理（設定・初期化・判定・保存・履歴）
│   ├── Index.html       … 画面の骨組み（全画面を 1 ファイルに持ち、表示を切り替える）
│   ├── Style.html       … CSS（<style> のみ）
│   └── JavaScript.html  … クライアント処理（<script> のみ）
└── docs/
    ├── DESIGN.md        … 本書
    └── （STEP 8 で）SETUP.md / TESTING.md / TROUBLESHOOTING.md
```

`Index.html` から `<?!= include('Style'); ?>` / `<?!= include('JavaScript'); ?>` で読み込み、HTML と JS を分離します。
判定ロジックは **Code.gs にだけ置く**（画面側と二重管理しない）方針です。

### 1-3. サーバー関数（google.script.run から呼ぶ API）

| 関数 | 用途 | 備考 |
|---|---|---|
| `setupSpreadsheet()` | シートと初期データを作成 | GAS エディタから手動実行。何度実行しても既存データは壊さない |
| `doGet()` | Web アプリの画面を返す | |
| `include(name)` | HTML 部品の読み込み | |
| `getInitialData()` | チェック項目マスターと設定を返す | 起動時に 1 回だけ呼ぶ（店頭での通信回数を最小化） |
| `evaluateCheck(payload)` | チェック結果から購入判定を計算 | 判定画面を開くときに呼ぶ |
| `saveRecord(payload)` | 商品情報＋チェック結果を保存 | LockService・入力検証・判定の再計算・重複防止 |
| `getHistory()` | 購入履歴の一覧（新しい順） | 一覧に必要な列だけ返す |
| `getRecordDetail(recordId)` | 1 件の詳細 | JSON を展開して返す |

シートが無い状態で呼ばれた場合は、各関数の入口で自動作成します。

## 2. 画面設計と遷移

```
 ホーム ──┬─▶ 古着の状態チェック ─┐
          ├─▶ 試着・フィット感チェック ─┤（どちらからでも、片方だけでも可）
          │                         ▼
          │                     購入判定 ──▶ 商品情報・メモ入力 ──▶ 保存完了
          ├─▶ 購入履歴 ──▶ 詳細
          └─▶ アプリの使い方
```

- 1 枚の HTML 内で画面（`<section>`）の表示・非表示を切り替えるだけのシンプルな SPA 構成です。
- 画面上部に固定ヘッダー（戻る／画面名）、チェック画面の下部に固定バー（進捗率・「判定へ進む」）を置きます。
- 状態チェックと試着チェックは同じ「現在のチェック」に記録され、両方やっても片方だけでも判定できます。

### 2-1. チェック項目の操作方法（★ご確認ポイント①）

項目文はすべて「〜ないか」という問いなので、**単純なチェックボックス 1 つだと「問題なし」と「まだ見ていない」を区別できません**。
判定の精度のため、各項目を次の 3 状態で扱うことを提案します。

| 状態 | 操作 | 意味 |
|---|---|---|
| 未確認 | 初期状態 | まだ見ていない |
| OK | チェックボックスをオン | 問題なしを確認した |
| 気になる | 項目右の「気になる」ボタン | 問題を見つけた |

- 進捗率 ＝（OK ＋ 気になる）÷ 対象項目数。カテゴリー別とチェック全体で表示します。
- 試着チェックでは、カテゴリー単位で「対象外」にできるようにします（例：ジャケットを買うときの「パンツのサイズ感」）。対象外のカテゴリーは進捗・判定に含めません。
- 古着ではなく新品の場合は、状態チェック自体を省略して構いません。

## 3. 購入判定ロジック

チェック数の多さではなく、**「気になる」項目の重大度**を優先して判定します。
状態（condition）と試着（fitting）をそれぞれ判定し、**悪い方を総合判定**にします。

| 優先 | 条件 | 結果 |
|---|---|---|
| 1 | `critical` の項目が 1 つでも「気になる」 | **見送り** |
| 2 | `warning` の「気になる」が 3 つ以上 | **見送り** |
| 3 | `warning` の「気になる」が 1 つ以上 | **要検討** |
| 4 | `normal` の「気になる」が 3 つ以上 | **要検討** |
| 5 | `critical` の項目に未確認が残っている | **要検討**（重大項目を確認していない） |
| 6 | 進捗率が 80% 未満 | **要検討**（確認不足） |
| 7 | 上記いずれにも当たらない | **買い** |

- しきい値（3 つ、80% など）は Settings シートで変更できるようにします。
- 判定画面には **理由**（例：「重大：虫食いや小さな穴がある」）を一覧表示し、
  「この判定は参考情報です。最終的な判断はご自身で行ってください」と必ず表示します。
- 商品情報入力画面の「総合判定」は自動判定を初期値にし、**ユーザーが変更できます**（最終判断はユーザー）。
  自動判定の結果は JSON 側に別途記録します。

```json
{
  "version": 1,
  "auto_judgment": "要検討",
  "reasons": ["注意：脇の下に汗ジミがある"],
  "progress": { "condition": 0.95, "fitting": 0.85 },
  "excluded_categories": ["C. パンツのサイズ感"],

```
`status` は `ok`（OK）／`concern`（気になる）／`unchecked`（未確認）。

## 5. 実装上の方針

| 要件 | 対応 |
|---|---|
| 非同期処理 | すべての `google.script.run` に `withSuccessHandler` / `withFailureHandler` を付け、通信中はローディング表示 |
| 競合防止 | `saveRecord` で `LockService.getScriptLock().waitLock(10000)`、`finally` で必ず解放 |
| 二重保存防止 | ①画面側：保存ボタンを無効化＋送信中フラグ ②サーバー側：record_id（画面で 1 回だけ発行）が既に存在すれば追記せず既存を返す |
| 入力検証 | 画面側（即時エラー表示）とサーバー側（最終チェック）の両方。サーバー側の検証を正とする |
| XSS 対策 | ユーザー入力は `textContent` / `createElement` でのみ描画し、`innerHTML` に入れない。テンプレートで `<?= ?>`（自動エスケープ）以外の出力をしない |
| 数式インジェクション対策 | `=` `+` `-` `@` で始まる文字列はシートに書く前に先頭に `'` を付ける |
| シート自動作成 | 各 API の入口で `ensureSheets_()` を呼び、無ければヘッダー付きで作成 |
| 判定の信頼性 | 保存時にサーバー側で判定を再計算（画面から送られた判定結果を鵜呑みにしない） |
| デザイン | オフホワイト背景 `#F7F5F0`／ネイビー `#1B2A41`／グレイ `#8A8D91`／ワインレッド `#7B1E2B`。見出しは明朝体（Noto Serif JP 系のシステムフォント）、本文はゴシック体。タップ領域は最低 48px。アニメーションは使わない |
| Web アプリ公開設定 | 実行ユーザー「自分」、アクセス「自分のみ」（個人利用を想定） |

## 6. ★ご確認いただきたい点

1. **チェック項目の 3 状態（未確認／OK／気になる）**：単純なチェックボックスだと判定が正しく出せないため提案しています。チェックボックス 1 つの方式が良ければ「未チェック＝要確認扱い」に変更します。
2. **重大度の割り当て**：上の表の critical / warning / normal で問題ないか。特に C16「カビ臭・タバコ臭・強い香水臭」は、要件どおりカビ臭を重視して critical にしていますが、タバコ臭・香水臭は洗濯で落ちることも多いため、**「カビ臭」（critical）と「タバコ臭・強い香水臭」（warning）の 2 項目に分ける**ことをおすすめします。
3. **公開範囲**：「自分のみ」で良いか（家族や友人と共有したい場合は「Google アカウントを持つ全員」などに変更）。
